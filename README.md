# DOFLAB 陌生設備接手與連續取放實驗 V7.0

> **V7.0 開發版本。** 新增第二種模擬設備與通訊協定、手冊可不提供驅動範本、可選擇產生 XY 控制程式。驗證以離線 Node、無頭 Chromium 與模擬 API 為主；已有真實 Claude 無範本驅動＋產生控制程式的本機紀錄：P2、G3 在 seed 42（開發）與未用於開發的 seed 2026／3140／8675 共 10 組，皆 5/5；仍非統計結論。先讀 `docs/CODEX_HANDOFF.md` 與 `docs/VALIDATION_STATUS.md`。

直接開啟 `unknown-device-v7.0.html`，按「開始完整實驗」。預設與 V6.3 相同：VLAB-P2、提供手冊範本、內建 XY 控制器、離線規則代理、五回合；不會自行呼叫模型。新選項在「連線設定」頁。

## V7.0 新增

1. **第二種設備與通訊（VLAB-G3）**：直角座標龍門，兩個未知直線軸（軸向對應、正負方向、增益與行程皆隱藏），搭配與 P2 相同的已知升降／夾爪介面。通訊為二進位框架：`0xA5 | LEN | payload | XOR 檢查碼`，以小寫十六進位字串表示位元組；XY 為 int16 big-endian、刻度 10000。設備回覆錯誤碼（FRAME、CHECKSUM、NOT_READY、LIMIT、OPCODE、ARGUMENT、COLLISION）。主機端以受信任的協定設定檔（`src/protocols.js`）獨立驗證產生的驅動程式，不採信驅動程式自己的回報；定點協定的 XY 指令會先量化到 0.0001，ACK 必須完全一致。
2. **手冊不提供驅動範本**：設定「不提供範本」時，手冊移除 `sampleDriver`／`sampleDriverSource`，改提供機器可讀的 `protocolSpec`。Claude／Gemini 只能依協定說明與規格自行撰寫 encode/decode。離線模式改用**規則式規格產生器**（`src/driver-synthesizer.js`）依 `protocolSpec` 產生驅動；這是確定性的程式產生，不是語言模型，報告標示為 `offline-spec-synthesizer`。
3. **產生 XY 控制程式**：設定「產生控制程式」時，驅動測試通過後新增 `write_controller`／`test_controller` 兩個工具。控制程式是無狀態的 `control(state)`，只依相機像素與已確認的 applied／影像位移歷史決定下一步，在與驅動相同的隔離沙箱執行。必須先在 6 組合成設備（旋轉、通道交換、反向、位置相依非線性、行程邊界、到達後反向）全部到達，才允許 `start_control`；執行中若輸出越界或例外，主機不送出該動作並停止。離線模式提交的是**預寫參考模組**（`offline-reference-module`），不是模型產生的程式。

切換設備、範本或控制模式都在「連線設定」頁，套用後重新開始。`window.experimentLab.configure({device:'VLAB-G3', manualTemplate:false, controllerMode:'generated'})` 可供自動測試使用。

### 能力界線（V7.0）

- 兩種設備都是模擬。G3 與 P2 共用相同的升降、夾爪、平台與相機標記；跨設備只改變機構與協定，並非任意未知設備。
- 規格產生器只支援 `json-line` 與 `binary-frame` 兩個框架家族，依賴手冊提供的機器可讀規格；這是無範本**流程**的離線基準，不是「AI 從零寫出驅動」的證據。
- 控制程式的隔離測試是主機端合成模型，不是被評估的設備；影像偵測、任務前提與取放驗證器仍由專案預先實作。
- 真實模型產生的 V7 驅動與控制程式目前有 P2、G3 × seed 42／2026 各一次（皆 5/5）；尚無重複次數與統計比較。

## V6.3 模型等待與限流恢復

- Claude／Gemini 的相鄰決策請求，開始時間預設至少相隔 6 秒，約每分鐘 10 次。設定頁可調整為 0–120 秒，0 表示停用固定間隔。這不是帳號配額保證；每分鐘詞元量、每日額度或其他共用金鑰的程式仍可能觸發限制。
- HTTP 429 才會進入有限次冷卻重試，最多 2 次。優先使用服務端提供的等待時間；沒有可用提示時依序等待 30、60 秒。過長的等待會停止並保留進度，不會默默降低服務端要求的冷卻時間。
- 畫面區分「請求間隔等待」「API 限流冷卻」「等待 AI 回覆」，以本機計時更新倒數，不額外呼叫 API。播放快慢仍只控制介面的步驟間隔。
- 暫停按鈕改為「本步後暫停」；已開始的模型步驟會先完成等待及有限次重試，再停止自動執行。回覆驗證後才會產生可執行的工具提案，等待本身不會重送設備動作。
- 每次送出的請求，包括限流重試與格式修正，都計入既有總上限；五回合最多 500 次、單回合預設 80 次。等待不會重設預算或帳號每日額度。前端及本機橋接各自保留預算閘門。
- 匯出 JSON 的 `modelRuntime` 保留請求數、限流重試數、累計等待及最近 40 筆診斷，每一步保留當時摘要。診斷不記錄金鑰或完整請求內容。`driverRuntime` 仍專門記錄本機通訊驅動的執行環境。

V6.1 的第五回合已知失敗是本機驅動等待逾時，不能據此判定為 HTTP 429。本版增加 API 等待及節流能力；是否真的遇到限流，仍須由 HTTP 狀態與匯出診斷確認。

## V6.2 修正

- 使用者的 V6.1 紀錄已完成前四回合，第五回合接近 A 時停在驅動編碼等待逾時。最後一筆擬議移動未送出；252 筆已執行動作均有確認。此紀錄仍是四回合通過，不能改列為五回合成功。
- 將背景工作執行緒的「啟動等待」與「執行回覆等待」拆開，各預設 5 秒。等待時間包含排程及訊息傳送，不等於程式實際占用 CPU 的時間；舊版逾時紀錄無法區分兩者。
- 只有 `encode` 在啟動階段逾時、尚未送出程式或設備命令時，才建立新工作執行緒重試一次。執行回覆逾時、編譯或解碼不自動重試；設備交換不重送。已收到設備 ACK 後解碼失敗，會保留動作證據並停止後續控制。
- 「測試與紀錄」新增驅動請求、啟動重試與執行環境失敗計數。JSON 的 `driverRuntime.recent` 保留最近 40 筆分階段診斷；每步保留當時的摘要。`programErrors` 包含協定測試刻意觸發的程式拒絕，不能當成執行環境失敗次數。
- 保留 V6.1 的平台標記修正、原驗證門檻與呼叫預算。檔名、介面、報告、原始碼套件及啟動器統一標示 V6.2，請下載新版原始碼並重新啟動橋接。

## 這一版測試什麼

- 首回合夾具從相機畫面的左下方待命位置出發。這是可達起始姿態，不是已學會硬體歸零。
- A、B 相隔更遠，五組位置與方向可重現；每回合使用同一部手臂、同一相機、同一通訊連線。
- B 高度依序為桌面、低台、高台、低台、桌面。數值 0 / 0.35 / 0.65 為相對安全升起高度，沒有毫米標定。
- 首回合執行外觀假設、查閱手冊、選端點、連線、握手、生成並測試驅動，再試動學習 XY 控制。
- 成功後重新 hello 握手，再調整 A/B，保留原驅動及局部 XY 映射。每回合重新取得夾取、共動、放置及退出證據；誤差過大仍可重新校正。
- 「測試與紀錄」列出每回合結果、誤差、動作數與呼叫數。中途停止會保留已完成回合，不會把部分完成顯示成五回合成功。

## 如何使用 Claude 或 Gemini

從 HTML 的設定頁下載完整原始碼 ZIP，解壓至新資料夾。

- Claude：執行 `start-lab.cmd`，預設使用 `ANTHROPIC_API_KEY`。若要用先前的名稱，可執行 `python claude_bridge.py --key-env ANTHROPIC_API_KEY_Extra --open-browser`。
- Gemini：執行 `start-gemini.cmd`，使用 `gemini_api_key`；找不到時以隱藏輸入提示提供。
- 啟動器先建置同版本 HTML。開啟後確認標題是 **V7.0**，在設定頁取得可用模型、選定模型及請求間隔、套用，然後開始實驗。
- 五回合前端預設總呼叫上限 500；單回合預設 80，可設定 1–500。橋接程序 CLI 預設上限為 500，`--max-calls` 可降低。前端及橋接會各自檢查上限，以先達到者為準；橋接計數涵蓋同一次啟動中所有實驗，重新整理頁面不會重設它。
- 上限是最多請求數，不是完成所需的保證。格式修正與限流重試也計數，達上限保留結果並停止；不會偷偷換成離線策略。

新版橋接可使用 `python claude_bridge.py --html unknown-device-v7.0.html --max-calls 500 --open-browser`。請下載本版內附原始碼、關閉舊橋接，再重新啟動；新版橋接會保留經過篩選的等待提示供前端判斷。詳細連線見 `docs/claude.md`、`docs/gemini.md`。

## 高度與程式生成的能力界線

這仍是 2R 平面機構，加上**已知的升降及夾爪介面**。本版模擬 `down` 會下降至當地支撐面，`up` 到安全上位；它不是 AI 由相機學會任意 Z 位置。平台有實際支撐判定：物件釋放後落到該 XY 下方的支撐面，不會吸附 B。低空進入高台範圍會在整筆 XY 命令執行前拒絕，這是簡化碰撞模型，沒有完整接觸力學。

藍圈表示 B 的平面定位，紫圈表示平台頂面。控制器只從相機 RGBA 解析標記；放置驗證另比對放手時的物件高度與平台高度，退出後重新確認物件仍留在平台。3D 畫面讀取模擬真實狀態作展示，不能替代相機驗證。

Claude／Gemini 已可依手冊產生並執行 JavaScript `encode` / `decode` 通訊驅動。**XY 數值控制、任務先決條件、影像驗證器仍由專案預先實作**。離線模式使用手冊驅動範本，沒有語言模型參與。

## 接下來的兩個階段

1. 跨工作站：相機切換後重新辨識設備及端點，判斷是否已有相符驅動；相機座標變換後需重新校正，不能直接沿用前站 XY 映射。本版尚未做跨站。
2. AI 產生運動控制器：模型讀取通訊與試動資料，生成受限控制模組，先通過隔離測試與獨立驗證，再執行。需與既有數值控制基線比較成功率、命令數及失敗恢復，不以程式碼生成成功代替取放成功。
